FoodShare Full Project Documentation

Repository overview • frontend + backend • process report • updated 10 October 2026

1. Project Summary

FoodShare is a full-stack food donation and sharing platform. The repository contains a Vite + React frontend and a Spring Boot microservice backend. The application supports donor actions, NGO/volunteer collection workflows, admin management, login/signup flows, and food listing operations.

Key note: Frontend and backend must run together for the project to be fully functional. The frontend communicates with the backend through the API gateway on http://localhost:8079/api.

5. Frontend Run Process

  1. Go to project root.
  2. Install dependencies: npm install.
  3. Run the project: npm run dev.
  4. Open the local port shown in the terminal browser window.
  5. For production check: npm run build, npm run check, and npm run preview.
# Frontend commands
npm install
npm run dev
npm run build
npm run check
npm run preview

# optional custom API base
VITE_API_BASE_URL=http://localhost:8079/api npm run dev

6. Backend Run Process

  1. Create all required MySQL databases: foodshare_auth_db, foodshare_food_db, foodshare_user_db.
  2. Update datasource credentials inside each service's configuration file.
  3. Start the services in order: service registry → API gateway → auth service → food service → user service → request/payment services.
  4. Verify discovery and health from http://localhost:8761/.
  5. Call endpoints using the gateway URL http://localhost:8079/api.
# Example backend startup
cd Backend/service-registry
./mvnw spring-boot:run

cd ../api-gateway
./mvnw spring-boot:run

cd ../auth-service
./mvnw spring-boot:run

Important: Some shell scripts or logs may refer to outdated ports or services; the real implementation should be validated against the current project code and configuration files.

7. API Flow Summary

Authentication flow

  1. Client sends request to /api/auth/register or /api/auth/login.
  2. API gateway routes request to the auth service.
  3. Service validates data, hashes password, issues JWT if valid.
  4. JWT is used in Authorization header for protected API calls.

Food flow

  1. Donor creates a food listing through frontend.
  2. Request goes to /api/foods.
  3. Food service processes quantity, expiry, address, and listing metadata.
  4. NGO or volunteer sees available food items and can act on them.

User flow

  1. User pages collect identity and profile data.
  2. Profile and role-based behavior are handled through service-level logic.
  3. Multiple role pages share the same core application flow.

12. Current Risks and Improvement Areas

  • Duplicate user data: Both auth-service and user-service manage user information independently.
  • Security risk: Some service logic may not enforce strong password hashing or JWT authorization consistently.
  • Service route inconsistency: Some services are accessible directly while others go through the gateway.
  • Outdated startup scripts: Scripts should be validated against the real current backend modules.
  • Environment dependency: MySQL and Java runtime configuration must be correctly set before runtime testing.

13. Final Execution Recommendation

For a successful local project run, follow this sequence: prepare databases, start Eureka, start the API gateway, then start auth and food services, then the remaining business services, and finally run the frontend application. Validate the UI, API health, and route flow before moving to production deployment.

Current recommended flow: 1) frontend dependency setup, 2) database creation, 3) registry startup, 4) gateway startup, 5) auth + food services, 6) user/request/payment services, 7) frontend launch, 8) functional testing.
